# Техническое задание: сервис ИИ-консультанта

Статус: проект ТЗ. Нагрузка, SLA, сроки хранения и юридическая допустимость обработки требуют согласования до реализации.

Связанное ТЗ: [Чат на сайте компании](website-ai-chat-spec.md).

## 1. Назначение и границы

Создать самостоятельный сервис, который принимает сообщения через API, ведёт консультацию по утверждённой базе знаний, уточняет потребность пользователя и предлагает разрешённые действия. Сайт компании является одним из каналов доступа; логика консультации не переносится в сайт.

Первая версия: текстовые консультации, поиск по базе знаний, подбор услуги, предложение обращения и передачи специалисту.

| Функция | Владелец |
|---|---|
| Интерфейс и идентификация посетителя | Сайт |
| Проверка данных перед внешней передачей | Backend сайта |
| Исходные сообщения с ПДн, если хранение необходимо | Российский контур сайта |
| История, допущенная к передаче, и контекст консультации | Сервис консультанта |
| Intent, стиль общения, поиск и генерация | Сервис консультанта |
| Контакты, подтверждение и создание обращения | Backend сайта или CRM |
| Контроль качества ответов | Сервис консультанта |

## 2. Архитектура

Первая версия — модульный монолит со следующими модулями:

- API;
- управление диалогами;
- выполнение консультации;
- база знаний и поиск;
- адаптеры ИИ-моделей;
- инструменты и интеграции;
- управление конфигурацией и оценка качества.

Генерация и индексация выполняются фоновым worker. Задания и результаты сохраняются: перезапуск процесса не должен приводить к молчаливой потере операции. Конкретный стек и механизм фоновых заданий определяются отдельно. Выделение внутренних модулей в микросервисы для первой версии не требуется.

## 3. Диалоги и контекст

Сервис должен:

- создавать диалог и присваивать идентификатор;
- сохранять допущенные сообщения и ответы;
- предоставлять историю с пагинацией;
- хранить структурированное состояние консультации;
- обеспечивать порядок сообщений;
- поддерживать завершение и передачу сотруднику.

Состояние включает цель пользователя, выясненные факты и потребности, недостающие сведения, резюме, предложенное действие и его статус.

В первой версии допускается одна активная генерация на диалог. Для нового сообщения во время генерации рекомендуется возвращать состояние «ответ формируется», без параллельного изменения контекста. Политика должна быть отражена в API-контракте.

## 4. Поведение консультанта

Консультант должен:

1. Понимать вопрос с учётом предыдущих сообщений.
2. Отвечать по найденным источникам.
3. Уточнять вопрос при недостатке данных.
4. Помогать подобрать услугу.
5. Предлагать создание обращения и передачу специалисту.
6. Сообщать об отсутствии подтверждённой информации.

Intent и адаптация тона определяются внутри сервиса. Отдельный вызов модели для классификации каждого сообщения не обязателен.

Инструкции задают область компетенции, стиль, правила источников, условия уточнения и передачи человеку. Запрещено выдумывать цены, условия и результаты действий. Сообщения и документы считаются данными, а не разрешением менять инструкции или права доступа.

## 5. База знаний

Предусмотреть загрузку, обновление, публикацию, исключение из поиска, версионирование и контроль индексации документов. При разбиении на фрагменты сохранять контекст источника. Ответы связывать с использованными источниками.

Документ содержит название, источник, версию, дату обновления и область доступа. Поиск учитывает организацию и права до передачи материалов модели. Черновики и закрытые документы недоступны публичной консультации.

Актуальные цены, статусы и другие изменяемые данные получать через API соответствующих систем.

## 6. Действия и интеграции

Предложение действия возвращается структурированно:

```json
{
  "type": "create_request",
  "proposal_id": "…",
  "requires_confirmation": true,
  "data": {
    "service_code": "financial_director",
    "summary": "Пользователь ищет сопровождение финансов компании"
  }
}
```

Создание обращения в первой версии выполняет backend сайта после подтверждения пользователя. Сервис принимает результат: выполнено, отклонено или ошибка. Сообщать об успешном создании можно только после подтверждённого результата.

Инструменты имеют фиксированные схемы аргументов, ограничения доступа и таймауты. Повторы не создают дубли.

## 7. API

Версионированный контракт, например `/v1`:

| Endpoint | Назначение |
|---|---|
| `POST /v1/conversations` | Создать диалог |
| `POST /v1/conversations/{id}/messages` | Принять сообщение |
| `GET /v1/operations/{id}` | Статус и результат |
| `GET /v1/operations/{id}/events` | Поток событий |
| `GET /v1/conversations/{id}/messages` | История |
| `POST /v1/conversations/{id}/action-results` | Результат действия |
| `POST /v1/conversations/{id}/close` | Завершить диалог |

Приём сообщения возвращает `202 Accepted`, `message_id` и `operation_id`: это приём задания, а не завершение консультации.

Обязательные поля: `client_message_id` или ключ идемпотентности, `request_id`, текст, разрешённый контекст и идентификатор канала. Повтор ключа с тем же содержимым возвращает существующую операцию; с другим содержимым — конфликт.

События: `started`, `delta`, `completed`, `failed`, `action_proposed`. Каждое имеет идентификатор. Переподключение восстанавливает пропущенные события в установленном окне хранения без повторной генерации.

Итог содержит текст, источники, предложения действий и признак необходимости сотрудника. Внутренние рассуждения модели не возвращаются.

## 8. Доступ, эксплуатация и качество

Обеспечить серверную аутентификацию приложений, изоляцию диалогов и знаний между клиентами, лимиты запросов и размера сообщений, времени, стоимости и числа вызовов инструментов.

Статусы операций: `queued`, `running`, `completed`, `failed`. Повторы внешних вызовов контролируются. Определить сроки хранения и удаление диалогов. В технических журналах не хранить секреты и необязательные ПДн.

Измерять время ожидания, время до первого фрагмента, полное время ответа, ошибки, потребление модели и результаты действий.

Создать контрольный набор вопросов и диалогов. Проверять ответы, источники, уточнения, действия и устойчивость к обходу инструкций при изменениях модели, инструкций и поиска.

## 9. Критерии приёмки

- История восстанавливается после переподключения.
- Повтор сообщения не запускает вторую генерацию.
- Недоступность модели приводит к явной ошибке.
- Используются разрешённые источники; отсутствие информации признаётся.
- Успех обращения не заявляется до результата.
- Чужие диалоги и закрытые знания недоступны.
- Задания и результаты переживают перезапуск worker.
- Контрольный набор проходит согласованные пороги качества.

## 10. Решения до реализации

Согласовать стек, страны и поставщиков агента, моделей, БД, логов и резервных копий; разрешённые данные; нагрузку и SLA; сроки хранения; источники знаний и ответственных; контракт обращений; канал передачи человеку; пороги качества.

Маскирование контактов не является доказательством обезличивания. Юридическая допустимость обработки проверяется для реальной цепочки поставщиков до запуска.

Голос, пользовательские файлы, платежи и произвольные действия агента не входят в первую версию.

## 11. Практики построения чата

Следующие рекомендации уточняют реализацию этого ТЗ. Практики интерфейса реализуются каналами по связанному ТЗ сайта; сервис предоставляет необходимые статусы и данные.

| Область | Рекомендуемая практика |
|---|---|
| Простота | Одна модель и ограниченный набор инструментов. Отдельные классификаторы и несколько агентов добавлять по результатам измерений |
| Общение | Сначала прямой ответ, затем необходимые пояснения; один основной уточняющий вопрос за ход; учитывать уже полученные ответы |
| Тон | Спокойный, уважительный, без давления. Не зеркалить агрессию и не считать предполагаемую эмоцию установленным фактом |
| Источники | Ссылаться на материалы, действительно поддерживающие ответ. Проверять существование и доступность источников программно |
| Неопределённость | При отсутствии данных уточнять или предлагать человека. Не использовать самооценку уверенности модели как единственное основание ответа |
| Память | Последние сообщения + структурированные факты + резюме + релевантные источники в пределах бюджета контекста. Хранить происхождение фактов; позволять пользователю исправить их |
| История | Сообщения являются источником истории; резюме — производное представление. Не превращать предположения агента в подтверждённые факты |
| Поиск | Начать с проверяемого базового поиска. Сравнить полнотекстовый, семантический и гибридный поиск на своих вопросах; reranking вводить при измеримом улучшении |
| Стриминг | Частичный текст считать предварительным. Канал отмечает завершение только после `completed`; структурированные действия публикуются после валидации |
| Надёжность | Идемпотентность на входе, устойчивое выполнение фоновых заданий, ограниченные повторы и восстановление результата после обрыва |
| Действия | Разделять предложение, подтверждение, выполнение и результат. Доступ и подтверждение проверяет код, а не модель |
| Человек | После подтверждённой передачи остановить автоматические ответы до явного возобновления; передать сотруднику разрешённое резюме |
| Изменения | Версионировать модель, инструкции, конфигурацию поиска и индекс знаний. Сравнивать версии на контрольных диалогах |
| Обратная связь | Собирать оценку ответа и причину проблемы; не добавлять непроверенную переписку автоматически в базу знаний или обучение |
| Данные | Изолировать память, поиск и кеши по клиентам и правам; не сохранять содержание диалогов в диагностике по умолчанию |

Основание для рекомендаций: [простые workflows и агенты](https://www.anthropic.com/engineering/building-effective-agents), [управление контекстом](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents), [проектирование инструментов](https://www.anthropic.com/engineering/writing-tools-for-agents), [оценка качества агентов](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents). Механизм идентификаторов и переподключения SSE описан в [MDN](https://developer.mozilla.org/en-US/docs/Web/API/Server-sent_events/Using_server-sent_events); хранение и воспроизведение событий реализует сервис.

## 12. Поэтапный план реализации

Чек-листы ниже описывают будущую приёмку: они не означают, что реализация уже выполнена. Каждый этап завершается демонстрацией результата и сохранением отчёта проверок. Нагрузочные и продуктовые пороги фиксируются на этапе 1, а не выбираются после получения результатов.

| Этап | Результат | Зависимость |
|---|---|---|
| 1 | Согласованные сценарии, контракты и критерии | — |
| 2 | Надёжный API диалогов без реальной модели | 1 |
| 3 | Консультант с моделью и памятью в тестовом контуре | 2 |
| 4 | Ответы по управляемой базе знаний | 3 |
| 5 | Поток ответов и восстановление | 4 |
| 6 | Подтверждаемые действия и передача человеку | 5 |
| 7 | Эксплуатация, безопасность и нагрузочные проверки | 6 |
| 8 | Интеграция сайта и ограниченный пилот | 7 |

### Этап 1. Сценарии, границы и контракт

**Цель:** определить проверяемую первую версию и согласовать взаимодействие сервиса с каналами.

**Задачи:**

- Описать консультацию, подбор услуги, уточнение, отсутствие ответа, обращение и передачу человеку.
- Установить владельцев данных, допустимый контекст и требования к размещению всей цепочки обработки.
- Выбрать стек, хранение, механизм фоновых заданий и поставщика модели с обоснованием.
- Подготовить OpenAPI и схемы событий, ошибок, действий и аутентификации; определить изоляцию клиентов и идентификацию диалогов.
- Установить нагрузку, p95 времени первого фрагмента и полного ответа, стоимость консультации, лимиты и сроки хранения.
- Подготовить стартовый контрольный набор: рекомендуется не менее 50 вопросов и 15 многошаговых диалогов, включая ошибки, неоднозначность и отсутствие источника. Зафиксировать критерии оценки и пороги.

**Чек-лист готовности:**

- [ ] Перечень сценариев и границы первой версии зафиксированы.
- [ ] Контракты доступны командам сервиса и сайта; примеры запросов и результатов согласованы.
- [ ] Зафиксированы стек, размещение, владельцы данных и ограничения передачи.
- [ ] Численные пороги качества, нагрузки, задержек и стоимости установлены.
- [ ] Контрольный набор содержит ожидаемые факты, источники, действия и допустимые варианты поведения.

### Этап 2. API, хранение и выполнение операций

**Цель:** получить устойчивый каркас, который можно интегрировать без зависимости от ИИ-поставщика.

**Задачи:**

- Реализовать диалоги, сообщения, операции и историю со стабильным порядком и пагинацией.
- Реализовать аутентификацию, проверку принадлежности объектов, валидацию и ограничения входа.
- Обеспечить атомарное принятие сообщения и фиксацию задания; исключить потерю между записью в БД и передачей worker.
- Реализовать ключи идемпотентности и ограничение одной генерации на диалог с защитой от гонок.
- Добавить восстановление зависших операций, владение заданием worker и защиту от повторной записи завершённого ответа.
- Использовать тестовый адаптер модели; реализовать ответы и ошибки по контракту.

**Чек-лист готовности:**

- [ ] Создание диалога, отправка, статус и история работают по контракту.
- [ ] Параллельные повторы одного сообщения создают одну операцию; изменение содержимого с тем же ключом отклоняется.
- [ ] Два разных сообщения не запускают параллельную генерацию в одном диалоге.
- [ ] Перезапуск worker и сбой после принятия задания не теряют сообщение.
- [ ] Повторное выполнение не дублирует сохранённый ответ; гарантия отсутствия повторной оплаты внешнего вызова не заявляется без поддержки поставщика.
- [ ] Проверены запреты доступа к чужим диалогам, операциям и истории.

### Этап 3. Модель и многошаговая консультация

**Цель:** реализовать понятное общение и управляемую память в закрытом тестовом контуре.

**Задачи:**

- Подключить одну модель через адаптер с таймаутами, лимитами и учётом потребления.
- Версионировать инструкции и проверять структурированный вывод по схеме.
- Реализовать ответы, уточнения, intent и тон без обязательного отдельного классификатора.
- Реализовать бюджет контекста, резюме и факты с происхождением и исправлением пользователем.
- Ограничить число ходов инструментов и повторы; не выполнять бизнес-действия.
- Проверить поведение на тестовых материалах. Публичную консультацию по фактам компании до этапа 4 не запускать.

**Чек-лист готовности:**

- [ ] Консультант учитывает предыдущие сообщения и не повторяет уже закрытые вопросы на контрольных диалогах.
- [ ] Исправление пользователя обновляет контекст; предположения не становятся подтверждёнными фактами.
- [ ] Длинный диалог укладывается в бюджет контекста с сохранением ключевых сведений.
- [ ] Таймаут и невалидный вывод дают контролируемую ошибку без бесконечных повторов.
- [ ] Для ответа фиксируются версии конфигурации, потребление и задержка без записи внутреннего рассуждения.
- [ ] Проверки общения проходят пороги этапа 1.

### Этап 4. База знаний и достоверность

**Цель:** обеспечить проверяемые ответы на основе опубликованной информации.

**Задачи:**

- Реализовать загрузку, версии, публикацию, индексацию и исключение документов.
- Сохранять источник и область доступа каждого фрагмента; применять фильтры до генерации.
- Выбрать поиск по результатам контрольного набора; отдельно измерять нахождение нужных материалов и качество ответа.
- Валидировать ссылки и соответствие источников ответу; определить поведение при конфликте или отсутствии информации.
- Обеспечить согласованную публикацию индекса: не выдавать смесь незавершённых версий.
- Проверить инструкции, внедрённые в документы, и отсутствие утечки закрытых материалов.

**Чек-лист готовности:**

- [ ] Ответы ссылаются на существующие разрешённые источники.
- [ ] Обновление, снятие и удаление документа отражаются в поиске и связанных кешах в установленный срок.
- [ ] Черновики и материалы другого клиента не попадают в контекст модели.
- [ ] При отсутствии источников консультант уточняет или предлагает сотрудника.
- [ ] Пройдены пороги качества поиска и фактической обоснованности ответов.
- [ ] Вредоносные инструкции из документов не разрешают новые действия.

### Этап 5. Стриминг и восстановление чата

**Цель:** предоставлять быстрый отклик без потери результата при обрыве соединения.

**Задачи:**

- Реализовать SSE, идентификаторы и порядок событий, heartbeat и окно воспроизведения.
- Определить восстановление по последнему событию, поведение при истёкшем окне и получение итога через статус.
- Сохранять итог до публикации `completed`; закрывать поток после терминального события.
- Отличать разрыв соединения от отмены задания: закрытие вкладки не отменяет генерацию автоматически.
- Согласовать с каналами обработку предварительного текста, ошибок и исключение дублей.
- Проверить таймауты и буферизацию реального reverse proxy.

**Чек-лист готовности:**

- [ ] Обрыв и переподключение не запускают новую генерацию.
- [ ] События восстанавливаются по порядку, повторные события не дублируют текст в тестовом клиенте.
- [ ] После истечения окна клиент получает сохранённый итог или явный статус операции.
- [ ] Ошибка после частичного ответа не отображается как успешное завершение.
- [ ] Для завершённой операции история и итог совпадают.
- [ ] Задержки и число соединений соответствуют порогам этапа 1.

### Этап 6. Действия и передача сотруднику

**Цель:** превращать консультацию в подтверждённый результат без самовольных действий модели.

**Задачи:**

- Реализовать предложения действий и состояния: предложено, подтверждено, выполняется, выполнено, отклонено, ошибка.
- Связать подтверждение с диалогом, пользователем, сроком действия и конкретными аргументами; изменение аргументов требует нового подтверждения.
- Принимать результаты только от авторизованного backend канала, с идемпотентностью.
- Интегрировать создание обращения на стороне сайта или CRM без передачи контактов в сервис.
- Реализовать передачу человеку, статус владельца диалога и разрешённое резюме; остановку и явное возобновление автоматических ответов.
- Проверить недоступность внешней системы, повторы и противоречивые результаты.

**Чек-лист готовности:**

- [ ] Предложение действия не выполняет его самостоятельно.
- [ ] Просроченное, чужое или изменённое предложение нельзя выполнить по старому подтверждению.
- [ ] Повтор результата не создаёт второе обращение и не меняет успешную операцию на противоречивый статус.
- [ ] Об успехе сообщается только после подтверждённого выполнения.
- [ ] При передаче сотруднику агент прекращает ответы; недоступность сотрудника объясняется без ложного обещания передачи.
- [ ] Сквозной сценарий обращения проходит через тестовый backend канала.

### Этап 7. Эксплуатационная готовность

**Цель:** обеспечить контролируемую нагрузку, восстановление и безопасную эксплуатацию.

**Задачи:**

- Настроить метрики, трассировку по `request_id`, предупреждения об ошибках, задержках, очереди и бюджете.
- Реализовать квоты, ограничение конкурентности, backpressure и обработку перегрузки.
- Проверить отказы модели, worker, БД и интеграций, ротацию секретов и изоляцию всех хранилищ.
- Реализовать сроки удаления, резервное копирование и проверенное восстановление; определить обращение с удалёнными данными в резервных копиях.
- Выполнить нагрузочные проверки, проверку журналов и полный контрольный набор.
- Подготовить инструкции запуска, обновления, отката, разбора инцидентов и аварийного отключения генерации.

**Чек-лист готовности:**

- [ ] Подтверждены согласованные p95 задержек, пропускная способность и стоимость.
- [ ] Перегрузка даёт контролируемый отказ, без неограниченного роста заданий.
- [ ] Проверены восстановление резервной копии и удаление по политике хранения.
- [ ] Секреты и непредусмотренные ПДн отсутствуют в диагностических журналах.
- [ ] Изоляция клиентов проверена для истории, поиска, событий, действий и кешей.
- [ ] Пороговые проверки качества пройдены; инструкции эксплуатации и отката доступны.
- [ ] Выполнены применимые требования CI и Production Gate проекта, где будет размещён сервис.

### Этап 8. Интеграция сайта и пилот

**Цель:** проверить реальную полезность консультанта и готовность общего решения к выпуску.

**Задачи:**

- Подключить сайт по отдельному ТЗ; проверить санитайзер, идентификацию, восстановление и форму обращения.
- Проверить исходящие данные во всей цепочке, включая контекст, результаты действий и мониторинг.
- Запустить ограниченный пилот с лимитами, ответственным за разбор проблем и возможностью отключения.
- Собирать обратную связь и оценивать долю корректных консультаций, обращения, передачу человеку, задержки и стоимость; не оптимизировать конверсию ценой достоверности.
- Разобрать ошибки, дополнить контрольный набор и повторить проверки после исправлений.
- Зафиксировать решение о выпуске, ограничениях или продолжении пилота по критериям этапа 1.

**Чек-лист готовности:**

- [ ] Сквозные сценарии вопроса, уточнения, обращения, отказа и передачи сотруднику пройдены.
- [ ] Проверены реальные исходящие запросы; ограничения передачи соблюдаются.
- [ ] Санитайзер и документы обработки проверены отдельно; тесты маскирования не заявлены юридическим доказательством обезличивания.
- [ ] По итогам пилота подготовлен отчёт качества, задержек, стоимости и проблем.
- [ ] Нет открытых критических дефектов доступа, потери данных и неподтверждённых действий.
- [ ] Выпуск соответствует установленным порогам; ответственные и способ отката определены.

## 13. Последующие улучшения

После пилота при подтверждённой необходимости: улучшение поиска и reranking, более экономичная маршрутизация моделей, дополнительные каналы, отдельный классификатор intent, голос и файлы. Для каждого улучшения фиксировать проблему, исходную метрику, ожидаемый эффект и проверку отсутствия регрессий. Дообучение и несколько агентов вводить после сравнения с более простым решением.
